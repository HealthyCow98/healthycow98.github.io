답을 찾은 직후에는 해결 과정이 선명합니다. 시간이 흐르면 어떤 가정이 틀렸고, 왜 그 방법이 동작했는지부터 잊기 쉽습니다. 이 블로그는 그 사이를 메우기 위한 기술 학습 기록입니다.

## 해결에서 이해로

좋은 학습 기록은 변경한 파일의 목록보다 질문에서 시작합니다. 어떤 조건에서 문제가 생기는지, 어떤 원리로 해결할 수 있는지, 그 방법이 적용되지 않는 경우는 무엇인지 순서대로 살펴봅니다.

실제 업무의 이름과 데이터를 지워도 기술적인 질문은 남을 수 있습니다. 다만 이름만 바꾼다고 모든 구현이 공개 가능한 것은 아닙니다. 고유한 업무 규칙을 걷어내기 어렵다면 기록을 보류합니다.

## 가장 작은 가상의 예제

다음은 반복 실행의 결과를 생각해 보기 위한 가상의 예제입니다. 실제 서비스의 코드를 가져온 것이 아닙니다.

```python
def remember_once(seen, item):
    if item in seen:
        return False
    seen.add(item)
    return True
```

같은 항목을 다시 전달하면 두 번째 호출은 집합을 바꾸지 않습니다. 하지만 이 함수만으로 여러 프로세스가 동시에 실행되는 환경의 중복 처리를 막을 수는 없습니다. 상태를 공유하는 방식과 확인·기록의 원자성을 함께 설계해야 합니다.

작은 예제는 원리를 분리해 보여줍니다. 운영 환경에서 필요한 조건을 생략했다면 그 한계도 설명해야 합니다.

## 자동화와 기록의 기준

글감 발견과 초안 작성에는 자동화 도구를 활용할 수 있습니다. 그러나 원본 소스를 그대로 옮기거나 확인하지 않은 실행 결과를 사실로 쓰지는 않습니다. 학습할 원리가 충분하지 않거나 공개 여부가 불명확한 글감은 남겨두고 검토합니다.

앞으로의 기록도 문제, 원인, 해결 원리, 가상의 최소 예제, 주의점이라는 순서로 차근차근 쌓아가려 합니다.
